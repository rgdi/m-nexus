## 1. Captura rápida

Un campo de texto. Todo lo demás pasa solo.

```
comprar pan mañana, llamar al dentista el viernes,
ir al gimnasio todos los días, pagué 40€ de la luz
```

| tipo | texto | |
|---|---|---|
| 🛒 compra | comprar pan | mañana |
| ✓ tarea | llamar al dentista | 2 oct |
| 🔥 hábito | ir al gimnasio todos los días | racha 🔥1 |
| € gasto | pagué 40€ de la luz | 40,00 € |

Nada se escribe hasta que aceptas el preview. Cuatro pestañas (Tareas,
Compras, Hábitos, Gastos) y un FAB flotante en móvil.

### Por qué reglas primero

Un thought que capturas caminando es justo lo que se teclea sin cobertura,
que es cuando más se capturan. Mandarlo a un LLM de pago en cada captura
es lento, cuesta dinero y falla justo cuando más se usa. El parser resuelve
el caso común con trabajo de strings; el modelo solo atiende lo que las
reglas no pueden cerrar.

Cada fila lleva `how` (`rule` | `llm` | `llm+rule`). La insignia dice
**"por reglas"** o **"revisado con IA"** según la verdad.

### El bug de los acentos

`\b` en JavaScript está definido sobre `[A-Za-z0-9_]`, así que `é` **no**
es carácter de palabra y `/\bpagu[eé]\b/` nunca puede casar con "pagué":
la frontera se asserta entre un no-palabra y otro no-palabra.

Todas las palabras clave acentuadas — pagué, gasté, reunión, hábitos,
miércoles — eran inalcanzables y caían en la rama genérica.

Ahora se envuelven con lookarounds Unicode:

```ts
const LETTER = "[\\p{L}\\p{N}]";
const w = (p) => `(?<!${LETTER})(?:${p})(?!${LETTER})`;
```

Todos los patrones llevan la flag `u`, obligatoria para que `\p{L}` exista.
Hay un test que falla si algún patrón con `\p` se cuelga sin ella.

### El split

`"comprar pan y llamar al dentista"` son dos cosas.
`"necesito leche, huevos y papel higiénico"` es **una** compra.

El "y" solo parte cuando lo que sigue empieza una acción del vocabulario
completo, no solo los verbos obvios: `"comprar pan, pagué 40€ de luz"`
también se parte, aunque "pagué" no sea un verbo.

### API

```
POST /api/v1/tasks/capture        { text, useLlm?, persist? }
POST /api/v1/tasks/:id/habit-check
GET  /api/v1/tasks/summary?kind=shopping|habit|expense|task
```

`Task` gana `kind`, `amountCents`, `cadence`, `streakDays`, `how` y
`sourceText` — **todo opcional**, para que las filas anteriores sigan
intactas.

`/api/v1/tasks` sale de `PUBLIC_PATHS`: la bandeja de captura contiene
listas de la compra, hábitos y gastos.

## 2. RAG con scoping por carpeta

Pregunta sobre **una** carpeta y recibe una respuesta construida solo con
lo que hay dentro, con las citas a la vista.

```
scope=Genética   q="¿qué es el gen CFTR?"   → 2/3 passages, 2 citas
scope=Genética   q="bicarbonato"            → 2/3 passages, 0 citas  ← la nota de
                                                                          Química está
                                                                          bloqueada
scope=Biología   q="bicarbonato"            → 2/3 passages  (incluye subcarpetas)
scope=(toda)     q="mendel"                 → 3/3 passages, 1 cita
```

El filtro de carpeta es un **scope duro**, no un peso en el ranking: una
pregunta sobre Genética nunca devuelve un passage de Química por parecerse.

### Tres fases, no una consulta

La arquitectura viene de
[open-notebook](https://github.com/lfnovo/open-notebook) (`graphs/ask.py`):

1. **Estrategia** — el modelo lee la pregunta y la descompone en hasta 5
   búsquedas, cada una con su término y su instrucción.
2. **Fan-out** — cada búsqueda corre por separado contra el mismo scope.
3. **Síntesis** — una pasada más fusiona las respuestas parciales, con el
   razonamiento de la estrategia a la vista, citando ids.

`"¿Qué sé del sistema nervioso y cómo se relaciona con el
gastrointestinal?"` son dos preguntas. Recuperarlo como un bloque devuelve
el chunk con mejor score y tira la otra mitad en silencio.

Sin modelo, o si la fase 1 falla, el resultado es **una** recuperación
léxica sobre la pregunta completa: el usuario nunca queda peor que antes.

### Dos detalles copiados porque rompen en producción

- Un modelo de razonamiento puede gastar todo su presupuesto pensando y
  devolver una estrategia sintácticamente válida **con los términos
  vacíos**. Se descartan, y si no queda nada usable se cae al camino
  determinista en vez de lanzar cinco búsquedas vacías y responder "no
  documents found".
- El prompt de síntesis prohíbe inventar ids y exige el id completo. Un
  id parafraseado es un enlace muerto.

### RRF, de SurfSense

[`chunks_hybrid_search.py`](https://github.com/MODSetter/SurfSense/blob/main/surfsense_backend/app/retriever/chunks_hybrid_search.py)
fusiona un brazo full-text y otro vectorial con **Reciprocal Rank
Fusion** sobre un FULL OUTER JOIN de Postgres.

La razón para usar RRF en vez de una suma ponderada: BM25 y coseno
producen números en escalas que no tienen relación entre sí. Cualquier
`lexical * 0.7 + semantic * 0.3` necesita normalizar ambos lados primero, y
esa constante se convierte en un hiperparámetro oculto que desordena en
cuanto cambia el corpus. La fusión por rango solo necesita el **orden** de
cada lista, que es estable.

```
score(d) = Σ 1 / (k + rank_i(d)),  k = 60
```

Hay un test que lo demuestra: con coseno a 1000 y 0, y ambos chunks
igualmente buenos en el braço léxico, los totales fundidos salen
**exactamente iguales**. Esa empate es la prueba de que la magnitud del
1000 no influyó.

### Tope por documento

También de SurfSense (`_cap_chunks_per_document`). Sin él, una nota larga
—un semestre de anatomía— llena la lista de resultados con sus propios
chunks consecutivos, y las otras cuatro notas que el usuario preguntó
nunca aparecen. Se limita a 3 chunks por nota, y como la lista llega
ordenada por score, la cabeza es la parte que coincidió.

### API

```
GET  /api/v1/rag/folders   — picker: cada carpeta + nº de passages
POST /api/v1/rag/ask       — { question, folderId?, shallow?, useLlm?, history?, allowWeb? }
GET  /api/v1/rag/status
POST /api/v1/rag/reindex
```

El índice vive en el servidor. El cliente ya no decide qué ve el modelo, así
que dos dispositivos haciendo la misma pregunta sobre la misma carpeta
reciben la misma respuesta — que es justo lo que significa anclar la
respuesta a una carpeta.

Las notas invalidan el índice al escribirse; la reconstrucción es perezosa,
así que solo la siguiente pregunta la paga.

## 3. El companion de IA, en popup

**Ctrl/Cmd+K** desde cualquier pantalla. Se abre en la ventana flotante de
v2.34.0: arrastrable y redimensionable en escritorio, hoja inferior en
móvil, **sin cambio de ruta**, para que la conversación sobreviva mientras
navegas.

### Qué se tomó de Khoj

[khoj-ai/khoj](https://github.com/khoj-ai/khoj) es la referencia para la
forma conversacional. Dos detalles importan más que el resto:

**Los subqueries se generan con el historial de conversación**, no solo
con el último mensaje (`routers/helpers.py::generate_online_subqueries`
pasa `chat_history` al prompt).

Esa es la razón entera de que sus respuestas se sientan continuas:
`"¿Y el tratamiento?"` recupera sobre la enfermedad que se estaba
discutiendo, no sobre las dos palabras "el tratamiento". Sin historial
cada pregunta de seguimiento es un arranque en frío — y un arranque en
frío no encuentra nada, que es indistinguible de no tener notas.

**La búsqueda es una herramienta, no un preámbulo.** Khoj expone la
búsqueda online como tool que el agente puede llamar. Aquí la decisión se
toma en el servidor, donde sí se puede ver si el índice local tenía algo.

### Dos cosas que deliberadamente NO se hacen

- **El fallback web está apagado por defecto** y etiquetado cuando se usa.
  Las notas son el producto; mandar una pregunta a un buscador es una
  decisión del usuario, no de la app. Un resultado web **nunca** se
  presenta como cita: una cita es una nota a la que se puede hacer clic.
- **Nada se afirma como cita si no salió del índice local con un noteId.**

### API de la conversación

```jsonc
POST /api/v1/rag/ask
{
  "question": "¿Y el tratamiento?",
  "history": [                       // ← lo que hace posible el seguimiento
    { "role": "user", "text": "¿Qué es la fibrosis quística?" },
    { "role": "assistant", "text": "..." }
  ],
  "folderId": "f-gen",
  "useLlm": true,
  "allowWeb": false
}
```

El historial se limita a los 6 turnos más recientes en el prompt: más que
eso es ruido para un modelo que solo necesita resolver la referencia.

### Búsqueda web (opcional)

Adaptada de `processor/tools/online_search.py` de Khoj, que extrae y lee
las páginas detrás de un resultado en vez de handing al modelo un snippet
— un snippet son 200 caracteres de texto SEO que no responden nada.

No hay API key de búsqueda en este proyecto, así que consulta el endpoint
HTML de DuckDuckGo y degrada a nada si no responde. Se marca en el log.

## 4. Un barrido por ruta

`scripts/capture_routes.cjs` lee `ROUTES` de `main.js`, visita las 22
rutas a tamaño de teléfono y registra qué encuentra.

**22/22 limpias.** Capturas en `screenshots/routes/`, informe en
`screenshots/routes/_report.json`.

Lo que cuenta como defecto:

- **404** — el cliente pidió un endpoint que no existe. La ruta nunca se
  cableó, o se cableó bajo otro path o prefijo.
- **5xx** — el servidor explotó sirviendo una petición normal.
- errores de red — una conexión rechazada significa que cliente y servidor
  no coinciden sobre dónde vive la API.

Lo que **no** cuenta:

- **401/403** — es una decisión de auth. Un no-admin abriendo Ajustes recibe
  un 403 de `/admin/ai`, la pantalla ya lo maneja y la página se renderiza.
  Marcarlo escondería los 404 de verdad.
- logs `info`/`debug` — la app escribe uno por arranque, por diseño.

El barrido encontró cuatro cosas rotas que nadie había visto:

### 4.1 `deviceRoutes` registrado sin prefijo

```ts
await app.register(deviceRoutes);              // → /devices/register
```
El frontend llama `/api/v1/devices/register` en cada arranque
(`services/device_id.js`). **404 en cada boot**, y con él todo lo
multi-dispositivo.

Al arreglarlo, Fastify se negó a arrancar:

```
Method 'GET' already declared for route '/api/v1/devices'
```

Porque `dashboard.ts` **ya declaraba** `GET /api/v1/devices`, y las dos
versiones habían divergido: una envolvía en `safeCall`, la otra devolvía la
lista cruda. La de `devices.ts` es la canónica; el duplicado se eliminó y se
conservó la forma más rica (`{ ok, count, devices }`).

### 4.2 La campana llamaba a un prefijo invertido

El backend expone `/api/v1/notifications-smart`. El widget pedía
`/api/v1/smart-notifications`. Nunca fueron la misma ruta, así que la
campana hablaba con la nada — y su `catch {}` se lo tragaba.

La v2.34.1 "campana de notificaciones pulida" salió mostrando cero, para
siempre. Faltaban además `unseen/count` y `mark-all-read`, que nunca
existieron. Los tres están ahora.

### 4.3 El backend escucha en 4000 y el frontend pedía 4100

`detectApiBase()` devolvía `http://localhost:4100` para desarrollo. El
servidor hace `config.port`, que por defecto es **4000**. Toda llamada
hecha sin override persistente iba a un puerto donde no escucha nadie.

Once archivos tenían el `:4100` hardcodeado, incluidos `notes.js` (13
ocurrencias) y el cliente WebSocket, cuyo socket **nunca** se conectó.

### 4.4 401 donde debía ser 403

`requireAdmin` respondía 401 ("tu token es malo") cuando el token era
perfectamente válido y lo único que faltaba era el scope admin.
`services/api.js` reacciona a un 401 **refrescando el token** — así que un
usuario no-admin disparaba un refresco que no necesitaba, y si ese refresco
fallaba la app lo echaba. **Abrir Ajustes expulsaba al usuario al login.**

403 dice "eres quien dices ser, y la respuesta sigue siendo no".
