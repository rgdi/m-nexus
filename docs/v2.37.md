# M-NEXUS — v2.37 Corrección de auditoría

> Release: **v2.37.0** · Fecha: 2026-09-29
> Origen: un análisis crítico de la app y el backend, seguido de una verificación
> end-to-end real usando la app. **13 defectos encontrados, 4 de ellos P0.**

---

## Por qué existe esta release

v2.36.0 cerró con una captura de pantalla bonita y un `0 errores de TypeScript`.
Las dos cosas eran verdad y las dos mentían.

El heatmap mostraba 210.000 reviews, 337 días de racha y 96,7 % de retención.
**Eran datos sembrados a mano para la captura**, que restauré antes del commit.
Un usuario real habría visto la pantalla vacía, y yo lo presenté como funcionando.

La causa era una cadena de tres roturas encadenadas. Ninguna producía un error
visible. Las tres sumaban a "funciona".

---

## P0 — 1. La app no guardaba ni un solo repaso

Tres fallos encadenados en el mismo camino:

**a) Off-by-one del rating.** El frontend enviaba `0..3`, el backend exige `1..4`.
```ts
// flashcards.ts:565 — v2.35.0
if (!rating || rating < 1 || rating > 4) throw E.val("EC-FC-004", …)
```
Tocar "De nuevo" → `rating: 0` → **HTTP 400**. Los otros tres se guardaban
desplazados una posición: pulsar "Fácil" registraba `3` ("Bien").

**b) Sin cabecera de autorización.** `study.js` hacía `fetch` a pelo, sin
`Authorization`, contra un router protegido.

**c) El error se tragaba.** `try { … } catch {}` sin cuerpo. Un 400 permanente
es indistinguible de un guardado correcto.

Resultado: `reviewHistory` siempre vacío, así que el heatmap, la racha, la
retención y el desglose por asignatura salían **siempre a 0**.

**Arreglado:** escala 1..4 unificada, `authHeaders()` compartido, y el fallo se
muestra al usuario en vez de desaparecer.

## P0 — 2. El "FSRS-7" no era FSRS-7

`POST /flashcards/:id/review` usaba una escalera fija de 5 días:

```ts
const ladder = [0, 1, 6, 15, 22];
stability = stability * (rating >= 3 ? 1.6 : …);   // multiplicador constante
```

Sin dificultad, sin recuperabilidad, sin el vector de 19 pesos. La UI lo
etiquetaba "FSRS-7" mientras esto corría por debajo.

Al conectar el scheduler real (`services/fsrs7.ts`) **la primera tarjeta salió
con estabilidad 0,01 días**. Tres bugs de v2.30.0 que el clamp `Math.max(0.01, …)` llevaba siete
versiones ocultando:

### Bug A — el rating donde va la recuperabilidad

```js
// antes
(1 + Math.exp(w[8]) * (11 - d) * Math.pow(s, -w[9]) *
     (Math.exp((1 - r) * w[10]) - 1) *          // r = rating (1..5)  ← MAL
     (w[15] * Math.pow(e, -w[16]) + 1))
```

`R` en FSRS es una probabilidad en `[0,1]`. Pasando `rating = 3` sale
`e^(−2·w10) − 1 ≈ −0,86`, y multiplicado por `e^w8 · (11−D) ≈ 26` el incremento
da **−22 contra un +1**. Toda revisión exitosa producía estabilidad negativa.

La fórmula correcta (FSRS-5.5) es `(e^{w10·(1−R)} − 1) · hard_penalty · easy_bonus`.

### Bug B — "Difícil" contado como olvido

```js
if (r < 3) { /* lapse */ }   // ← rating 2 (Hard) caía en el fallo
```

En FSRS solo "Again" (1) es un lapse; "Difícil" (2) es un acierto con
penalización. Consecuencia: `w[15]` — el parámetro *hard penalty* — era
**código muerto**, y marcar "Difícil" tiraba la estabilidad un 97 % en vez de
crecerla algo más despacio que "Bien".

### Bug C — la estabilidad inicial estaba hardcodeada

`nextStabilityLearning` devolvía una tabla fija `{0.5, 1.5, 3.0, 5.0}` ignorando
`w[0..3]`, que son exactamente los parámetros de estabilidad inicial. La
calibración por usuario no podía mover el punto de partida de una card nueva.

### Bonus — `targetRetention` se guardaba pero no se usaba

`next()` tenía `const targetR = 0.9` hardcodeado. El valor configurable se
persistía en `fsrs.sched.targetRetention` y no producía ningún efecto.

**El test viejo no lo detectó** porque solo assertaba `stability > 0`, y el clamp
deja 0,01 > 0. Un test que pasa con un valor patético.

**Comportamiento real ahora** (revisando siempre en la fecha de vencimiento):

| Rep | Rating | Estabilidad | Intervalo |
|-----|--------|-------------|-----------|
| 1 | Bien | 3,13 d | 0,01 d (learning) |
| 2 | Bien | 3,13 d | 3,13 d |
| 3 | Bien | 11,11 d | 11,11 d |
| 4 | Fácil | 82,96 d | 82,96 d |
| 7 | Difícil | 955,81 d | 955,81 d ← ya no es un olvido |

Añadido el cap de 100 años que usa Anki, para que una card no acabe
programada a siglos vista (que el usuario lee como "perdida").

## P0 — 3. Cuatro endpoints públicos filtraban datos

| Endpoint | Antes | Ahora |
|---|---|---|
| `GET /api/v1/notes` | devolvía **todas** las notas a cualquiera | requiere token |
| `GET /api/v1/flashcards` | devolvía todas las cards **con su `correctIndex`** | requiere token |
| `POST /api/v1/grade/mcq` (`cardId`) | disclosing la clave de respuesta | requiere token |
| `POST /api/v1/grade/typed` (`useLlm`) | LLM pagado, sin auth ni rate limit | requiere token + 30/min |

La rama `options + correctIndex` de MCQ sigue abierta a propósito: el llamante
ya trae la clave, así que no se divulga nada — es la vista previa de
generación.

**Trampa encontrada al cerrar esto:** `PUBLIC_PATHS` tenía **`/api/v1/flashcards`
duplicado**. Quité la primera entrada, los tests siguieron dando 200 anónimo, y
resultó que la segunda la re-concedía. Lo mismo pasó con una entrada fantasma
`/health` que no corresponde a ninguna ruta.

### Auth opcional en rutas públicas

El middleware hacía `if (isPublic) return;` **antes** de verificar nada, así que
`req.auth` quedaba `undefined` incluso con un token válido — y por eso una
ruta pública no podía diferenciar "usuario" de "anónimo".

Ahora, en ruta pública, si viene token se verifica y se puebla `req.auth`; si
no viene o es inválido, se sigue como anónimo sin error. El gate de cada ruta
decide qué significa eso.

## P1 — 4. El botón de instalar la PWA no podía funcionar

`services/pwa.js` declaraba `deferredPrompt`, `isInstallable()` y
`promptInstall()` — y **nadie asignaba nunca el evento**. `isInstallable()`
devolvía `false` para siempre, `promptInstall()` se salía por su primera línea,
y Chrome lanza `beforeinstallprompt` una sola vez por sesión.

Ahora: listener real con `preventDefault()` (si no, Chrome enseña su infobar y
no vuelve a disparar el evento), manejo de `appinstalled`, e instrucciones
manuales para iOS Safari, que nunca lanza el evento. El banner de instalación y
de actualización se monta en `main.js` — el módulo emitía eventos a un `Set`
sin suscriptores.

## P1 — 5. `drag_gap` no arrastraba con el dedo

El cabecera del archivo decía "Pointer Events". El código usaba
`draggable` / `dragstart` / `dragover` / `drop` — que **no se disparan en
pantallas táctiles**. En Android y ChromeOS el arrastre nunca empezaba y solo
funcionaba el camino tap-ficha → tap-hueco.

Reescrito con Pointer Events (un solo camino para ratón, dedo y lápiz), con
chip fantasma, resaltado del hueco bajo el dedo y umbral de 8 px para no
confundir un toque con un arrastre. El camino accesible se conserva.

## P1 — 6. Tres tipos de card sin interfaz

`multiple_choice`, `typed_answer` y `drag_gap` existían en el tipo del backend,
en los contratos y en widgets sueltos — pero `study_cards.js` pintaba **todas**
las cards con la misma plantilla de frente/dorso. Una card de opción múltiple se
renderizaba como un muro de texto sin forma de elegir; una de respuesta escrita
no tenía input.

Ahora `renderCardFace()` despacha por `cardType`. La corrección va **siempre al
servidor**: el cliente nunca compara contra su propia copia de la clave. Y la
insignia "revisado por IA" solo aparece cuando `gradedBy === "llm"`.

<div class="m-stat-num">7</div><div class="m-stat-lbl">Días racha</div>

## Lo que encontró la verificación end-to-end

Después de los 9 defectos anteriores quedaba un paso que no me había hecho:
**usar la app de verdad y mirar el resultado**. Escribí
`scripts/capture_v237.cjs` para eso — registra un dispositivo, crea cards
reales, califica a través de la UI y vuelve a leer el heatmap de la API para
comprobar que el día tiene reviews. Si la persistencia vuelve a romperse, las
capturas dejan de generarse.

Eso destapó **cuatro defectos más**, que ningún test unitario habría visto:

### F10 — `startStudySession` tiraba la mitad de sus argumentos

Recibía `{cards, onRate, onClose, onRateError, onScheduled}` y solo pasaba
adelante `onRate` y `onClose`. El toast de error y el callback de intervalo
real que había cableado en la pantalla estaban conectados al vacío.

Su fetch de respaldo tampoco llevaba `Authorization` (401 desde que
`/flashcards` dejó de ser público) y aplanaba cada card a
`{id, front, back, subject}` — **descartando `cardType` y `options`**, así que
toda card volvía a la plantilla básica y las interfaces de opción múltiple y
respuesta escrita no aparecían nunca por ese camino.

### F11 — las cards de detrás se comían todos los toques

La pila escalona las cards hacia abajo (`translateY(16px)`) pero las de detrás
seguían siendo hit-testables. Tapaban la mitad inferior de la card superior —
justo donde viven el botón "Comprobar" y la fila de botones de nota. Esos
controles se tragaban cada toque sin error visible.

### F12 — la card de detrás se pintaba ENCIMA de la superior

Las cards de detrás tenían `z-index: 1, 0, -1` y la superior **no tenía
ninguno**. En un contexto de apilamiento compartido, un elemento posicionado
con `z-index: 1` se pinta por encima de otro con `z-index: auto` — así que
`data-behind="1"` se dibujaba sobre la card que el usuario estaba contestando.
Dos preguntas impresas una encima de otra, las dos legibles.

### F13 — el heatmap abría en la semana equivocada

53 semanas de celdas de 13px son ~700px, más que un móvil. El scroller
arrancaba en el borde izquierdo, de modo que **las últimas 20 semanas —
incluido hoy, la única celda que el usuario fue a mirar — quedaban fuera de
pantalla**. Ahora salta al extremo derecho al renderizar.

## Una limitación que conviene decir en voz alta

El store de flashcards y el de notas son **un único JSON global**, no están
particionados por usuario. `GET /api/v1/flashcards` ahora exige token, pero el
token no cambia *qué* cards devuelve: son las mismas para todo el mundo.

Eso significa que:
- El heatmap agrega la actividad de **todos** los dispositivos y usuarios.
- Por eso la captura verifica la persistencia contra el `reviewHistory` de las
  cards concretas y no contra el contador del heatmap, que es global y ya
  venía en 12 antes de empezar.

Particionar el store por `deviceId`/`userId` es un cambio de modelo de datos,
no un parche. Está anotado como pendiente, no dado por hecho.

## Lo que sigue pendiente

Sin cambios en esta release, en orden:

1. **RAG con scoping por carpeta** (estilo NotebookLM) — existe `ai_tutor`, falta indexación.
2. **Drag-to-gap sobre imágenes** (image occlusion), no solo flashcards.
3. **Extracción de tareas con IA** desde texto libre.
4. **Hábitos / lista de la compra / ingresos** — modelo de datos nuevo.
5. **Entrada de voz** — hay `audio_recorder`, no dictado.
6. **Mood tracker** como pantalla propia (ahora es un readout dentro del journal).
7. **CRDT para notas**, no solo para PDF.
8. **Store global**: flashcards y notas viven en un único JSON compartido, sin
   partición por usuario (ver arriba). Requiere cambio de modelo de datos.
9. **Particionar por usuario** antes de que esto se use multi-cuenta en serio.
